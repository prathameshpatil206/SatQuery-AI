# SatQuery-AI: Comprehensive "A to Z" Technical Report

## 1. Project Overview & Objective
**SatQuery AI** (Problem Statement: SIH26167) is an advanced agentic vision-language assistant for multimodal remote-sensing and satellite image analysis. The system receives natural language queries and satellite imagery from users, autonomously identifies the user's intent, routes the data through specialized computer vision models, and returns highly detailed text insights and geographic coordinates.

---

## 2. Information Sources (Inputs)
The system receives input primarily through a `POST /query` HTTP endpoint, exposed by the FastAPI backend, using a `multipart/form-data` payload:
1. **`query` (Text)**: The natural language prompt from the user (e.g., "Highlight the water body", "Find new construction between T1 and T2").
2. **`image` (File - Optional)**: The primary satellite image file (typically a `.tif` GeoTIFF, or `.png`/`.jpg`).
3. **`image_t2` (File - Optional)**: A secondary temporal image used specifically for bi-temporal change detection (comparing a scene "Before" and "After").
4. **`image_sar` (File - Optional)**: A Synthetic Aperture Radar (SAR) image file, used in conjunction with the primary optical image for cloud-penetrating or multimodal analysis.

---

## 3. System Outputs
Regardless of the complexity of the query, the backend normalizes all results into a strict, unified JSON contract expected by the frontend. 

**Standard Output JSON Structure**:
- `task` (String): The classified intent (e.g., `"grounding"`, `"vqa"`, `"change_detection"`).
- `query` (String): The parsed original user prompt.
- `answer` (String): The natural language findings/text answer generated by the vision agent (e.g., Florence-2 or the change detection heuristic).
- `confidence` (Float): A confidence score between 0.0 and 1.0.
- `spatial_data` (GeoJSON `FeatureCollection`): Polygon or point data of detected objects or changed zones. This is heavily normalized (using EPSG:4326/WGS84) to be directly injected into a **Leaflet map**.
- `visual_evidence` (Object): Contains a `preview_data_url` (Base64 PNG string) to display a low-latency preview of the raster directly in the UI.
- `raster_overlay` (Object): Supplies Leaflet with `bounds` (min/max latitude and longitude) and a base64 URL so the raw satellite image is perfectly draped over the real-world map.
- `execution_trace` (List): An array of internal steps with `time_ms` indicating execution time, used to animate the frontend's loading sidebar.

## 4. Codebase Walkthrough: What Each Part is Doing

### A. The Agentic Backend (`backend/`)
This is the central nervous system that coordinates user requests, LLMs, and Vision models.

1. **`backend/main.py` (The API Server)**
   - **Role**: Initializes the FastAPI app with CORS middleware and exposes endpoints (`/health`, `/history`, `/query`).
   - **Flow**: 
     - Receives `POST /query`.
     - Calls `_save_upload()` to temporarily save images to `data/uploads/`.
     - Calls `classify_intent()` from `router.py` to figure out what the user wants.
     - Conditionally calls the correct specialist function (`run_detection`, `detect_change`, or `analyze_optical_sar`).
     - Uses `rasterio` and `PIL` to generate a base64 `raster_overlay` preview.
     - Logs the entire transaction into SQLite.
     - **Fail-Safe Mechanism**: Wraps the entire execution in a `try...except` block. If the server lacks RAM, a model crashes, or the network drops, it immediately loads a perfect demo response using `load_cached_fallback()` to guarantee the frontend never receives a 500 Error.

2. **`backend/router.py` (Intent & Spatial Normalization)**
   - **`classify_intent_gemini()`**: Sends the user's text to Google Gemini (via HTTP API) along with metadata (`has_t2`, `has_sar`). Gemini returns a strict task string.
   - **`classify_intent_fallback()`**: If Gemini is unreachable or rate-limited, this zero-dependency regex engine reliably classifies the intent based on keywords (e.g., "change", "radar", "highlight").
   - **`normalize_spatial_geojson()`**: A critical function. Vision models output pixel coordinates (e.g., x=150, y=200). This function uses `rasterio.warp.transform` to read the CRS (Coordinate Reference System) embedded inside the `.tif` file and projects the pixels into real-world WGS84 Longitude/Latitude bounds for accurate Leaflet mapping.

3. **`backend/database.py` (SQLite Persistence)**
   - **Role**: Maintains local auditability. Every query, its generated JSON response, and execution metrics are logged into `data/satquery.db`. 

### B. The Vision Engine (`vision/`)
This module actually looks at the pixels, runs the heavy machine learning models, and computes geographical bounding boxes.

1. **`vision/detection.py` (Single-Image Grounding & VQA)**
   - **Role**: Uses the **Florence-2** Vision-Language Model.
   - Handles `vqa` (Visual Question Answering), `caption` (Scene Summarization), and `grounding` (locating specific objects like "Find all water bodies").
   - Translates bounding boxes predicted by the ML model into Python dictionary contracts (`GroundingResult`).

2. **`vision/change_detection.py` (Bi-Temporal Analysis)**
   - **Role**: Compares a `T1` and `T2` image to identify what has changed over time.
   - **Algorithm**: Validates spatial alignment, calculates pixel-wise spectral difference (Change Vector Analysis/CVA), and applies Otsu's Thresholding to isolate statistically significant changes (like deforestation or new construction). Calculates a percentage of area changed.

3. **`vision/optical_sar.py` (Multimodal Analysis)**
   - **Role**: Fuses traditional Optical/Multispectral images with Synthetic Aperture Radar (SAR) backscatter images.
   - It cross-references both modalities. For instance, clouds block optical cameras but SAR sees right through them, allowing the system to verify water bodies (low optical reflectance + specular SAR reflection) or buildings (dihedral SAR backscatter) in any weather condition.

4. **`vision/geospatial.py` (GIS Math & I/O)**
   - **Role**: Handles raw array manipulation. Loads `.tif` images with `rasterio`, normalizes 16-bit satellite bands into 8-bit displayable RGB arrays, and defines the mathematical functions mapping local image pixels to global coordinates (`pixel_to_geo`).

5. **`vision/types.py` & `vision/__init__.py`**
   - **Role**: Defines Pydantic/dataclass schemas representing the output payload to ensure type safety. Exposes high-level import statements so the Backend can easily consume the Vision Engine.

### C. The Frontend (`app/`, `components/`)
*(Note: As indicated by `package.json` and React code)*
- Built on **Next.js 14**, utilizing a 40/60 Split-Screen layout.
- The left sidebar houses the chat interface where users type prompts and view the textual `answer` and live animated `execution_trace`.
- The right viewport uses **React-Leaflet**. When it receives `spatial_data` (GeoJSON), it automatically places interactive polygon overlays and renders the raw satellite image (`raster_overlay.url`) perfectly pinned to its geographic `raster_overlay.bounds`.

## 5. System Resilience Summary
SatQuery-AI is architected specifically for high-stress demonstration environments (like Hackathons):
1. **LLM Redundancy**: Gemini API failure triggers a deterministic RegEx keyword router.
2. **Vision Model Redundancy**: If Florence-2 runs out of memory or OpenCV fails on a weird TIF format, `main.py` intercepts the exception and serves a cached success state from `sample/cached_demo_results.json`.
3. **Spatial Redundancy**: If an image lacks an EPSG projection (CRS) in its metadata, the system synthetically anchors the bounding boxes to a demonstrative center point in India, ensuring the UI map never crashes on empty coordinates.
